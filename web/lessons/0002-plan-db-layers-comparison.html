单元 2：各层数据库/数据表的核心区别

掌握全链路血缘后，业务与研发最常问的问题是：“**既然已经有了估值流水表和核心日净值表，为什么还要分 5 层？它们在数据颗粒度、存储与计算逻辑上有何区别？**” 本课将从 4 个维度对比这 5 层结构。

1. 五层数据结构多维对比总览

来源：字段级清洗逻辑总表.md 来源：MPRF_F_PLAN_DAYNETVALUE调用梳理.md
层级 数据颗粒度 (Granularity) 存储与形态 (Persistence) 核心职责 (Primary Responsibility) 典型代表
1. 源数据与维表层 细粒度 (按估值科目/证券明细) 物理数据表 (ODS 流水) 忠实记录交易流水与科目明细，不做跨日期连乘或多计划汇总。 MFACTGZ_FUND_HLDTOTAL
2. 清洗与计算函数层 逻辑计算过程 PL/SQL 存储过程 / 自定义函数 无状态清洗规则封装（区间过滤、剔除组合加权、几何连乘）。 DW_ZNST_INDEX_NEW
3. 核心计划日数据层 中粒度 (单计划 + 每日) 物理数据表 (DW 核心事实表) 持久化单个计划每日的标准净值、日收益率与报酬，是 SQL 唯一事实依赖。 MPRF_F_PLAN_DAYNETVALUE
4. SQL 查询汇总层 粗粒度 (多计划明细 + 合计) SQL 动态查询逻辑 (UNION ALL) 多口径应用级汇总，拆分为期末加权、总体函数、逐日加权及历史直读。 查询 SQL UNION ALL
5. 输出指标层 指标级 (四组业务 KPI) 前端应用层输出/展示列 为前端/报表展示提供业务语义化的指标分组（基础/收益/报酬/风险）。 RYIELDG, F_VIX 等

2. 核心解耦边界剖析

① 为什么 DW 层 (第 3 层) 与 ODS 层 (第 1 层) 必须解耦？

ODS 估值流水表 MFACTGZ_FUND_HLDTOTAL 包含大量如 701A、702A 的底层会计科目，且持仓报酬分散在 HLDDETAIL 中。如果前端查询 SQL 直接读取 ODS 流水，每次查询都需要现场关联多个流水表并计算复杂的现金流收益率，查询性能极差且极易出错。DW 核心表 MPRF_F_PLAN_DAYNETVALUE 预先清洗并落库了单计划每日的标准值，极大地提升了查询性能。

② 为什么 DW 层 (第 3 层) 不直接存储“合计行”指标？

因为 SQL 合计行的汇总口径是动态的（取决于前端传入的计划范围过滤条件 VC_PLAN_TYPE 以及查询开始日与结束日 beginDate / endDate）。合计行的收益率必须根据所选范围内的计划，现场调用总体加权函数 GET_OVERALL_WEIGHTED_RETURN_W 或按期末资产净值动态加权，因此合计行只能在 SQL 查询层 (第 4 层) 现场计算。
