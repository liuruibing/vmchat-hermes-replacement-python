# 合并规则

## 前置条件

只有模块、子模块、指标、展示范围和合并意图已明确，才能进入合并审查。

- 模块、子模块或指标缺失：停止并使用自然语言反问，不审查合并，不返回 JSON。
- 展示范围、图表类型或合并形态含糊：停止并使用自然语言反问，不审查合并，不返回 JSON。
- 命中与展示意图完整且唯一：才允许审查多模块是否可合并。

合并结论为可合并或条件已满足的条件合并后，才能构建 DSL。
不可合并时必须使用自然语言直接驳回并给出 catalog 依据，不得生成或返回 JSON。

## 审查顺序

必须检查全部维度后再给出结论。

仅有一个语义数据源且不存在跨数据集组合时，不执行合并审查，也不向用户输出内部判断对象。

| 维度 | 可直接合并 | 条件合并 | 不可合并 |
|---|---|---|---|
| 分析对象 | 对象与粒度一致 | catalog 已提供同粒度结果 | 产品与个券之间需要临时聚合或展开 |
| 数据形态 | 同为时序或同为截面 | 返回结果已具备共同维度 | 需要临时重塑才能关联 |
| 时间粒度 | 日期与频率一致 | 返回结果已是相同频率 | 需要临时重采样或查询期间不可比较 |
| 业务含义 | 同一业务概念 | 用户明确比较不同指标，并保留独立名称 | 字段含义不明确或被错误视为同一指标 |
| 单位 | 单位一致 | table 保留独立单位；ECharts 最多使用两个纵轴 | 单位不明却被放到同一纵轴，或需要三个以上纵轴 |
| 方向 | 方向一致 | 增加盈亏方向 | 合并后方向丢失 |
| 分类体系 | 分类体系一致 | 保留分类体系字段 | 将不同体系代码视为同一值 |
| 合并键 | 存在稳定共同键 | 共同键存在但需确认唯一性 | 不存在可信合并键 |
| 基数关系 | 一对一 | catalog 或用户能确认一对一 | 需要临时聚合、去重或存在多对多 |

## 判定流程

必须先判断用户的“合并”是哪种形态，再套用合并规则。不得跳过意图形态判断。

### 1. 识别合并形态

**横向关联**：用户说“放在一起、同表展示、对比、一起看、合并展示”，且没有明确要求把两份结果拼成同一行集或同一指标列时，默认按横向关联审查。

**纵向拼接**：用户明确说“拼成一个列表、合成一列、统一排行、追加到下面、把 A 行和 B 行混在同一个指标列里、增加一列类型区分”时，按纵向拼接审查。

**意图不明确**：用户只说“合并一下”，且无法从上下文判断横向还是纵向时，不得自行选择；必须反问用户是要“按共同键横向对比”还是“拼成一个列表”。

### 2. 横向关联通过条件

同时满足以下条件时，横向关联结论为可合并或条件合并通过：

- 两个或多个数据集是同一分析对象粒度，例如同为产品-日期、同为行业、同为证券、同为分类项。
- 存在可从字段映射表确认的稳定共同键，例如日期、证券代码、行业代码/名称、分类名称。
- 共同键语义一致，且不需要临时聚合、重采样或拆分才能对齐。
- 用户选择的指标可以保留各自独立名称、单位、方向和来源，不会被错误合并为同一业务指标。
- 数据集合不完全重合时，可以用外连接表达，缺失侧填 `null`，且这种缺失不会改变业务含义。

横向关联通过后，transform 必须对共同键取合集、去重、排序，再按键回填各模块字段；某个模块缺少对应记录时，该模块输出字段填 `null`。集合互斥、部分重合或一侧缺失记录本身不是拒绝理由。

### 3. 方向或正负相反的处理

指标方向、正负号或名称相反不是自动拒绝条件。只要分析粒度和共同键成立，且输出中保留独立字段名、label、单位和来源，就可以横向关联。

必须拒绝的情况是：合并后会丢失方向或语义，例如把“收入/支出”“盈利/亏损”“买入/卖出”“流入/流出”强行合成同一列、同一指标或同一排序口径，而用户没有给出明确的归一口径。

### 4. 同名字段的处理

字段同名不代表可合并为同一列；字段不同名也不代表不可合并。

- 同名字段若业务含义、方向或单位不同，必须输出为不同字段和不同 label。
- 不同字段若业务含义一致、单位一致、方向一致，且 catalog 或用户问题能证明同一个共同键不会同时出现多侧冲突值，才允许合并为统一输出字段。
- 仅凭指标名称相同、字段名相同、单位一致或业务描述相似，不足以把多侧字段合并为同一列。
- 同一个共同键在多侧都有值且用户没有指定冲突处理规则时，不得静默覆盖；应保留来源字段，或反问用户。
- 禁止使用 `a ?? b`、`a || b`、`a !== null ? a : b` 等“优先取一侧、缺失再回退另一侧”的方式合并同义字段，除非 catalog 明确说明两侧结果集对该共同键互斥，或用户明确指定了这种优先级。
- 若两侧字段业务含义和单位一致，但无法证明互斥或值一致，应输出为带来源前缀的独立字段和 label，例如 `profitPositionRatio` / `lossPositionRatio`，不得合并成单个 `positionRatio`。

## 常见模式

### 纵向合并

跨模块纵向拼接当前不受支持。即使两个模块列结构相似，也不得把两者拼成同一行集或同一指标列；若未来 DSL 增加跨模块显式拼接契约，再重新开放。此限制不影响满足条件的跨模块横向关联，也不适用于同一父模块 MD 已明确授权的 `全部子模块：combined-table`；后者按 `dsl-spec.md` 的 Catalog 授权子模块组合规则执行。

### 横向关联

仅在两个数据集具有相同粒度的稳定共同键、且共同键在查询结果内可形成一对一关系时使用。共同键和用户选择的指标必须分别通过各模块 MD 字段映射表确认 JSON 路径、原始字段，并结合模块概览、指标业务说明或 `metrics.md` 确认语义一致，但这些内部依据不写入前端 DSL。由 `transform.function` 按解析结果读取各模块响应，按共同键取合集、去重和排序，再回填用户选择的字段，缺失值补 `null`。禁止仅凭字段同名认定可关联、指定某个请求为主数据源或按数组下标拼接。

### 聚合后关联

当前精简 DSL 不表达聚合。个券明细与产品级结果需要聚合后关联时，应说明所需聚合口径并停止生成；不得把产品指标复制到每条个券记录。

## 必须拒绝

- 不存在共同或可信的关联键。
- 未选择日期或聚合规则，就把每日时序数据与区间截面直接关联。
- 分析对象不同，且不存在聚合或展开规则。
- 展示名称相同，但业务含义冲突。
- 不保留分类体系，就直接合并不同分类体系的代码。
- 多对多关联没有去重或聚合规则。
- 只能通过数组下标对齐两份结果。
- catalog 缺少关键证据，无法判断。
- 用户指标无法在字段映射表中唯一定位，或字段映射与示例 JSON 冲突。

## 拒绝时的用户提示

拒绝或信息不足时，不得返回 JSON 或只返回结论代码。必须使用自然语言直接告诉用户：

- 哪些模块和字段参与了判断；
- 哪些维度发生冲突或缺少信息；
- 每个判断对应的 catalog 事实；
- 为什么这些冲突会导致无法生成可执行 DSL；
- 用户可以如何修改问题或补充条件。

若存在替代方案，可以建议分别展示、先聚合到同一粒度、选择明确日期或保留区分维度，但不得在用户确认前擅自改变原问题。
