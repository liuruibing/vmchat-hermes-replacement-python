01THE BIG PICTURE

先分清三个问题。

Runtime 管“这次任务如何运行”，Workflow 管“业务如何完成”，Provider 管“怎样访问模型”。三层协作，代码的位置才有意义。

RUNTIME / 运行框架

接入与生命周期

main.py 规范请求、准备上下文、认领任务、发送 SSE、保存会话与产物。它是共享基础设施。

WORKFLOW / 业务流程

步骤与分支

Engine → Registry 找到实例，再调用 stream(context)。内部可以是 LangGraph，也可以直接写 Python。

PROVIDER / 模型适配

调用与工具

封装模型客户端、生成、工具交互与 usage。服务启动配置或注入决定 Provider；Agent 指定业务 workflow。

02ONE REQUEST, END TO END

沿着一次请求，走完公共入口。

想象用户说“分析这份 PDF”，请求引用已上传的 document_id。同一套入口也可以承接“生成绩效报表”，只是后来选择的工作流不同。

01上传文档
POST /v1/documents
校验 PDF 类型、大小与签名；原始文件落盘，pypdf 按页解析。文档记录进入 ready，返回 ID；后续请求传 ID。
02规范化请求
POST /v1/runs
HermesCreateRunRequest → VmChatInput。从聊天数组选最后一个用户问题，结构化 context 优先，旧文字标记作回退。
03准备受限上下文
检查 Agent、文档、Skill 权限；SessionManager 提供历史，ContextManager 选相关内容并裁预算，更新 UI 摘要。
04保存 queued 任务
RunStore.create 保存请求和 prepared_input，返回 run_id 与 context 遥测。创建 run 本身尚未调用模型。
05认领并启动
GET /events
queued → running；重复执行返回 409，结束任务回放缓存。并发许可不足发送 run.failed。也可用 POST /start 在后台消费同一条事件生成器。
06组装并分派
读取 Agent 的 workflow、Role 的 systemPrompt、Skill；组装 WorkflowContext，把 Provider、知识检索和文档加载作为能力传入。
07消费业务事件
工作流交出 reasoning/message/completed/failed；HTTP 层累积正文、保留 metadata，并序列化成 data: JSON\n\n。等待期间每 12 秒可发保活注释。
08完成与保存
HTTP 层先发送完成帧，再尝试保存 DSL artifact 和成功轮次，最后标记 RunStore complete；finally 释放许可与活跃任务登记。

两种“拒绝”发生在不同时间

执行前：请求无效、未知 Agent、文档未 ready、上下文超预算，会返回 HTTP 错误，此时任务尚未成功创建。

执行中：并发不足、模型错误、业务校验耗尽或取消，走 run.failed。不进入正常保存成功轮次的路径。

已结束：事件缓存能回放，但只存在当前进程的 RunStore 内；它不是跨进程消息队列。

同一个入口，五种走法。

选择路线，然后逐步点击节点。每一步都回答：谁给它数据、它做什么、输出给谁。这里演示的是源码中的逻辑顺序，不会发送真实请求。

报表路线的关键回路

为什么需要 candidate_dirty？刚生成的新候选必须校验；修复返回普通文字等无效结果时，候选没有改变，重复验证同一份草稿没有收益。计数仍递增，确保流程能退出。
04MANDATE RISK V2

先理解原文，再关联指标。

V2 的目标是“帮用户选择与合同相关的指标”。它产出指标、理由、匹配分和原文依据。默认筛选与详细审计是两种不同深度。

DEFAULT / SCREENING

直接筛选

PDF 条款 × 完整指标库 → 每行判断 → 校验 → 聚合。

  • 默认每批 40 行，并发 2，文档窗口约 60000 字符。
  • 每批全部库行恰好一项，DIRECT/REVIEW 需要原文 ID。
  • 跨窗口保留关联，指标得分取最高关联分。
  • coverage_status=not_audited；SRC 包装用于展示证据。
OPT-IN / DETAILED

提取、审计、映射、复核

Phase A 建立完整要求 IR，Phase B 映射指标并交 Critic 独立审核。

  • 先保留主体、测量、约束、范围、条件、例外、关系与证据。
  • 每条 clause 都有 coverage 账目，完整才进入映射。
  • 默认每批 8 行，并发 2；映射关系是多对多。
  • Critic 默认审核一次，有异议降级待复核。

两种身份，撑起证据链

箭头表示身份传递。最终页码与文字来自解析源，不采信模型复制出的引用；偏移量相对于解析文本，不是 PDF 视觉坐标。

一个要求可以对应多个指标

# 关联示意；不是本次模型运行输出
REQ-0001 ──→ row_id A
     └─────→ row_id B
REQ-0002 ──→ row_id A

# 最终按指标聚合
row_id A:
  requirements: [REQ-0001, REQ-0002]
  match_score: max(各关联分数)
  metric_name: 从真实指标库读取

row_id B:
  requirements: [REQ-0001]

输出字段各自表达什么

screened_metrics所有保留的筛选关联，按分数聚合排序。
matched_metrics筛选模式：有 DIRECT；详细模式：DIRECT 且 MAIN_TABLE 且未被拒绝。
candidate_metrics保留但未进入 matched 的关联；通常需进一步确认。
gap / pending / non-metric详细模式要求的其它去向；不能只看主表就认为要求都能由库指标表达。

repair 不是一种统一的“重试”

发生位置修什么当前默认边界
模型网络调用502/503、UNAVAILABLE 等瞬态传输问题最多 3 次；240 秒超时直接抛错
提取 / screening 批次输出形状、真实 ID、漏行等结构问题首次 + 1 次反馈重试
Coverage 输出逐条账目漏项、引用无效等审计结构问题首次 + 最多 2 次修复
完整 Phase A审计仍显示 MISSING / PARTIAL 的语义遗漏最多 3 轮提取 + 审计；仍不完整则关闭 Phase B
Mapping / 去向 / Critic 结构输出形状和引用不满足契约各阶段 1 次反馈重试
Critic 语义异议映射或最终去向不可信默认 max_critic_repairs=0；审核一次并落实降级，配置增大才重跑映射
结果的准确含义：match_score 是模型给出的文档相关程度，不是正确概率、风险值或合规结论。V2 没有持仓计算、SQL 执行或 DSL 生成；算法字段只是原始库信息。“覆盖完整”表示要求提取审计通过，映射仍可存在 gap / pending。Python 校验能保证形状与来源身份，语义正确性仍需要模型和人工判断。
05WHO OWNS THE DATA

四种状态，四种生命周期。

“有 state”不代表“会自动记住对话”。持久会话、任务执行、图检查点和大型产物承担不同责任。

Run

候选、错误、用量、节点结果。InMemorySaver 检查点重启即丢失，不替代会话库。

Artifact

结构化产物

SQLite 保存大型 DSL JSON，Session 留引用。当前公共保存逻辑识别 DSL，不保存任意 Markdown。

app/artifacts/store.py

持久数据 → 本次有限视野

Session 的完整消息经过“最近 + 相关旧消息”选择，再经 ContextManager 历史上限与总预算裁剪。较早内容形成确定性摘要。

页面 DSL 优先保留选中及相关块；不相关块用摘要。小页面（≤3 块）先保留完整；超预算再逐步降级未选中块。

保留的 DSL 自身仍超动态预算，会返回明确错误。

服务能力 → Context，轻量值 → State

WorkflowContext 放 Provider、资料与回调。节点闭包可访问这些能力；图 State 放当前执行的轻量中间值。

TypedDict 类似 TS interface；节点返回字典像 store patch。没有 reducer 时列表字段也是替换，所以 reasoning 与 usage 的累加必须显式写。

thread_id=run_id 仅区分检查点，不创建 Python 线程。

PDF 和知识库也各有归属：原始 PDF、解析 JSON 和文档索引由 DocumentService 管；document_id 是跨请求的引用。KnowledgeService 管 Agent 知识分块与检索，可配置 embedding，DuckDB 不可用会回退 SQLite。V2 当前读完整指标库分批审核，不使用这条 RAG 检索路径。
06ASYNC, EVENTS & TOOLS

异步把等待让出去，事件把结果交出来。

Provider 的流、Workflow 的生成器和 HTTP 的 SSE 是三个接口。串起来时，需要明确每一层何时产生事件。

# Python ↔ 前端类比（教学示意）
async def run():       # async function
  result = await work() # await Promise
  return result

async def stream():    # async function*
  yield progress       # 交出一项，之后继续
  answer = await run()
  yield answer

async for event in stream():
  send_sse(event)       # for await ... of

# 调用 async generator 不会一次跑完整函数
# 消费者取下一项，生成器才继续推进

当前的时间顺序

聊天 / 报表 / V1：先 await graph.ainvoke；节点可能消费模型流，但外部 stream 等图结束后才 yield 过程与正文。

V2：先 yield 明确的阶段进度，await 管线，Python 生成完整报告，然后切成正文片段。

HTTP：等下一个事件，12 秒没有结果就发 : keep-alive\n\n；保活不是正文，也不是重跑。

事件含义HTTP 层怎么处理
reasoning.delta模型可见过程或程序进度，不能统一理解为私有思考重新编号 sequence，过程和正文分开
message.delta用户可见正文片段累积 full_output，序列化并缓存 SSE 帧
reasoning.done过程区域结束收到过 reasoning 时，HTTP 层在成功结束发送
run.completed完整 output、usage、可选 metadataHTTP 层统一发送完成帧并执行后续保存
run.failed执行失败或被取消标记失败，退出正常成功路径，finally 释放许可

工具调用实际是一段受控的对话循环

@tool / bind_tools 给模型工具说明 → 模型返回 tool_call → Python 验证工具名/参数/次数 → 调用白名单回调 → 把 ToolMessage 放入 messages → 下一轮模型读取工具结果。它不是模型直接访问文件系统。

路径边界

资源 reader 拒绝绝对路径、反斜杠、.. 与未登记路径。工具回调只读取允许的资源。

调用边界

Provider.run_skill 限制总轮数（12）、资源读取次数（默认 24）、搜索次数（默认 6）和回填字符量。

上下文边界

Runtime 做 token 估算预算；reader 与工具回填限制字符量。两者不是同一个单位，也不替代业务输出校验。

　

取消的实际边界：连接断开/取消会触发生成器清理，工作流和 Provider 检查 signal；/cancel 可 abort 控制器并取消后台任务。它是协作式取消，不能承诺远程模型供应商立即停止生成或计费。Run 的 phase 字段也不会自动跟随每个图节点更新。

    自检：能解释这几个问题，就串起来了。

    为什么创建 run 成功后，还没有调用模型？

    create_run 只验证输入、裁上下文并保存 queued。GET events 的 claim 才把 queued 改为 running，随后事件生成器被消费才推进 workflow。POST start 通过后台消费这条生成器启动执行。

    换一个 Agent，一定会换模型吗？

    不会。Agent 配置选择 workflow/role/skill/knowledge；Provider 在 create_app 时由配置或注入决定。当前公共入口中，这两条选择分别生效。请求 model 字段并不等价于每次重建 Provider。

    为什么 SSE 有很多片段，也可能要等很久才看到正文？

    当前图工作流先等待 ainvoke 完成，再从最终结果切片 yield；V2 也先生成完整 Markdown 再切片。HTTP SSE 能分片运输，不代表业务层实时透传模型 token。

    TypedDict 和 Pydantic 都有类型，为什么不能互换理解？

    TypedDict 给静态类型工具描述字典字段，不会自动验证运行时值。Pydantic 的 model_validate 会检查模型输出形状与字段限制，但真实库行和证据身份等业务规则仍需专门校验函数。

    为什么 detailed 的 DIRECT 也可能最终不进 matched_metrics？

    direct_links 同时要求 DIRECT、最终 MAIN_TABLE 选中和未被 Critic 拒绝。MAIN_TABLE 校验允许 REVIEW，但 direct_links 不接收它，所以 REVIEW 仍归 candidate。默认 screening 则按窗口里是否出现 DIRECT 归类。

    Screening 输出有 requirements，是不是已经逐条提取合同？

    不是。这是为了复用结果展示结构生成的 SRC-xxxx 证据包装，类型 OTHER，attributes.screening_evidence=True。它没有经过 Phase A，也没有 coverage 审计；coverage_status=not_audited。

    Python 能保证模型的结论都正确吗？

    它能验证形状、库行身份、引用存在、账目完整、分数范围，并从权威数据回填名称和引文。语义判断、关联理由和评分仍由模型产生；coverage complete 也不能保证指标算法等价或实际合规。

    报表 DSL 和 SQL 到底是什么关系？

    vm-report 返回的是报表配置 JSON，包含请求模块/代码标识和视图描述，再由下游消费。本文核对的工作流负责生成与校验，不把“返回 DSL”画成 Python 执行持仓 SQL。V2 则直接返回风险指标报告，不接这条 DSL 路线。

    把新业务接入这套框架，需要改哪些位置？

    复用现有流程时，Agent 包声明 workflow、Role、Skill 和 knowledge 即可。需要新控制流时，实现有 id 和 stream(context) 的对象并注册；Runtime 仍消费同一套事件。接口约定让图技术和模型客户端可以各自变化。

    下一次排查问题，可以先定位所在边界：请求字段错 → normalize；记忆不对 → Session/Context；走错业务 → Agent/Registry；模型或工具错误 → Provider/reader；结果不合法 → 业务 validator；页面缺失结构化数据 → completed.metadata；长时间没正文 → 查看业务层是否在等待整图完成。
